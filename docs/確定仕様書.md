# SougeiShare-v2 確定仕様書

作成日：2026年10月10日  

## 1. 目的・基本方針

中学校の部活動の練習試合で、保護者が「行き」「帰り」の送迎を分担するWebアプリ。担当回数と走行距離を比較して、グループ内の負担の公平性を見える化する。職業訓練のポートフォリオとして制作する。

- アプリ名：**SougeiShare-v2**。
- 技術：Python / Flask / SQLite / HTML / CSS。Windows 11、VS Codeで開発・実行する。
- 追加ライブラリは必要最小限。Google Maps APIは使わない。
- 実際に公開し、グループの保護者に使ってもらうことを目指す。
- **スマートフォンでの利用が中心**。全画面をスマホ優先のレスポンシブデザインにする。

## 2. アカウント・グループ

### 2-1. 新規グループ作成

入力は次の**4項目**。

1. グループ名（1～30文字、日本語可）
2. 表示名
3. ユーザーID
4. パスワード

登録時に重複しない**数字6桁のグループコード**を自動生成する。グループと最初のユーザーを作成し、**登録後は自動ログイン**する。

グループコードは半角数字6桁で入力し、先頭の0も含めて6桁を保持する文字列として保存する（例：012345）。入力の前後の空白は自動で取り除く。

表示名は1～20文字で日本語を利用できる。入力どおりに表示し、敬称を自動追加しない。

### 2-2. 既存グループへの参加

入力は次の**4項目**。

1. グループコード
2. 表示名
3. ユーザーID
4. パスワード

有効なグループコードで既存グループに参加し、**登録後は自動ログイン**する。**人数上限なし**。

### 2-3. ログイン・ログアウト

- ログイン項目：**ユーザーIDとパスワードのみ**。グループコードの入力は不要。
- **ユーザーIDは全グループを通して重複不可**。
- ユーザーIDは半角英数字・`_`・`-`の3～30文字。大文字・小文字を区別する。
- パスワードは8～128文字。確認用の再入力欄は追加しない。入力の空白は勝手に削除しない。
- パスワードは平文保存せず、ハッシュ化して保存する。
- ログアウトボタンを設置し、CSRF対策付きPOSTでログアウトする。
- 初期ユーザー・仮の試合などの**サンプルデータ（seed）は作らない**。

### 2-4. グループ権限と分離

- 同じグループの全メンバーは、試合の閲覧・登録・削除、送迎担当の操作、履歴閲覧ができる。
- グループ管理者専用の権限・画面は設けない。
- グループの削除も、利用中の同グループ全メンバーが可能。
- **グループコードは試合一覧画面から全メンバーが確認できる**。
- **他グループのユーザー・試合・履歴は表示・操作できない**。DB操作時もログイン中のグループIDで絞り込む。

## 3. 画面と機能

### 3-1. ログイン画面

ユーザーID・パスワード入力、ログイン失敗時の案内、新規グループ作成・既存グループ参加への導線を用意する。

### 3-2. 試合一覧画面

スマートフォンで見やすい**試合ごとのカード形式**を採用する。カードには次を表示する。

- 試合日（曜日付き）
- 会場名
- 中学校からの片道距離（km）
- 「行き」「帰り」それぞれの担当状態と操作
- 試合削除の操作

画面には「試合を登録」「担当履歴」「ログアウト」への導線と、グループ名・グループコードの確認手段を設ける。試合0件のときは、登録を促す案内を表示する。

練習試合一覧の日付区分は日本時間を基準とする。初期表示では今日以降の試合を日付の近い順に表示する。「過去の試合」に切り替えると、昨日以前の試合を日付の新しい順に表示する。過去の試合も保存され、担当履歴の集計対象となる。

#### 行き・帰りの状態

各方向は独立して次の3状態を持つ。

| 状態 | 意味 |
| --- | --- |
| 募集中 | まだ担当者が決まっていない |
| 決定 | グループ内の担当者1名が決定している |
| グループ外 | グループ以外の車で行く・帰る |

- 「担当する」でその方向の担当者を決定する。**各方向の担当者は1名だけ**。
- 同じ人が同一試合の行き・帰りの両方を担当してよい。
- 「グループ外」はその方向のみの設定で、担当履歴には加算しない。
- 担当の**取り下げができる**。**本人以外のグループメンバーも取り下げ可能**。
- 「決定」は「取り下げる」、「グループ外」は「募集中に戻す」で募集中へ戻す。いずれも確認メッセージを表示する。同グループの全メンバーが操作できる。
- 担当者の交代や決定からグループ外への変更は、一度募集中へ戻してから行う。
- 状態変更時に二重担当・他グループの操作が起きないようにする。
- 「試合削除」は**確認メッセージ**を表示し、担当情報が消えて履歴集計が変わることを説明する。「OK」で削除、「キャンセル」で中止。
- すべてのグループメンバーが試合を削除できる。

### 3-3. 試合登録画面

入力は次の**3項目**。

1. 試合日
2. 会場名
3. **中学校からの距離（片道km）**

- 距離は手入力。
- 距離は0～999.9km、小数第1位まで。
- 同じ日付・同じ会場の試合も複数登録できる。
- 正しい年月日なら、過去・今日・未来の日付を登録できる。
- 会場名は1～50文字。
- 曜日は試合日から自動計算して一覧に表示する。
- 登録直後の「行き」「帰り」は**両方とも募集中**。
- 登録した試合は同じグループの全メンバーに表示される。
- スマートフォンで入力しやすくする。

### 3-4. 担当履歴画面

**目的は公平性の比較**。個人別カードのみにはしない。

- **一覧表**：グループ全員の「表示名」「行き回数」「帰り回数」「合計担当回数」「総走行距離（km）」を横並びで比較する。
- **横棒グラフ**：メンバーごとの総走行距離を比較する。
- グラフは**HTMLとCSSのみ**で実装し、グラフ専用ライブラリを追加しない。
- **スマートフォンで横スクロールが発生しないことを重視**。列幅・文字サイズ・表示方法を調整する。データやメンバー数が増えてもレイアウトが崩れないようにする。
- グループ外の送迎は集計対象外。
- スマホでも5列の比較表を維持する。見出しは「表示名・行き・帰り・合計・距離（km）」とし、長い表示名は折り返す。
- 表の下に横棒グラフを表示する。表とグラフは合計担当回数が多い順。

#### 距離・回数の計算ルール

**旧Python版の計算方式を維持する。Java版で用いていた往復換算は使わない。**

- 担当回数＝行きの担当回数＋帰りの担当回数。
- 走行距離＝担当した各方向について、その試合の**片道距離を1回ずつ加算**。
- 例：片道10kmの試合で「行きのみ担当」→1回・10km、「行きも帰りも担当」→2回・20km。
- 「グループ外」「募集中」は0回・0km。
- 取り下げ・試合削除後は、現在の試合・担当情報から集計し直す。

### 3-5. ログアウト画面

ログアウト完了メッセージをログインフォームの上に表示する。スマートフォンでも上下配置で見やすくする。

### 3-6. 個別のアカウント退会

- ログイン本人だけが、自分のパスワード再入力と確認後に退会できる。
- usersに退会状態を記録してログインを停止。既存の他ブラウザのセッションも次のアクセスで無効化。
- 過去の担当実績は残す。日本時間の今日以降の担当は募集中へ戻し、更新番号も進める。
- 履歴とグラフに「（退会済み）」を表示。グループや他メンバーは削除しない。
- 同じユーザーIDの再登録・退会取り消しは対象外。最後の利用中メンバーの退会は注意を表示し、グループは自動削除しない。

### 3-7. グループ削除

- 同グループの利用中メンバーなら誰でも削除可能。作成者の記録・管理者権限は追加しない。
- 自分のパスワードと半角数字6桁のグループコードを再入力する。確認チェックと送信直前の確認メッセージを付ける。
- 全員のアカウント・試合・担当履歴が削除され、元に戻せないことを説明する。
- matches、users（退会済み含む）、groupsを同じ保存単位で所属グループだけ削除する。
- 他のグループには影響しない。削除後は全メンバーのログインを停止する。

### 3-8. 画面の文字・案内文

- 担当履歴、練習試合一覧、ログイン、グループ作成・参加の見出し下説明文は、小さい補足文と同じ0.8remにそろえる。
- 入力補足は各項目の規則を案内する。パスワードの補足表示は「8文字以上」とし、入力規則は2-3を参照。
- 送迎の担当状態は1.125remにし、太字と状態別色を維持する。

## 4. データベース設計の基本方針

業務データは次の3テーブルで管理する。列・制約・補助テーブルは[詳細設計5章](詳細設計.md#5-er図列設計)を参照。

- **groups**：グループID、グループ名、グループコード
- **users**：ユーザーID、表示名、パスワードハッシュ、所属グループID、利用中／退会済み
- **matches**：試合ID、所属グループID、試合日、会場名、片道距離、行き・帰りの状態と担当者

履歴は現在の担当情報を集計する（3-4）。ログイン状態・DB・入力検証の方式は詳細設計を参照。


CSRF対策を全POSTに適用する（方式は[詳細設計14章](詳細設計.md#14-実装時の共通処理)）。

公開先・公開手順は未確定。
