## 5. ER図・列設計

ER図はテーブルの関係を表す。PK＝行を識別する主キー、UK＝重複不可、FK＝別テーブルへの参照。

図：[ER図](diagrams/03.png)

- users.idは内部の数値ID。ログイン入力はusers.user_idで、全グループ共通のUNIQUE制約を付ける。
- groups.codeは数字6桁をTEXTで保存し、先頭の0を保持する。UNIQUE制約を付ける。生成衝突時は作り直す。グループ名・表示名は重複可とする。
- 必須列はNOT NULL、担当者列は未決定・グループ外の場合NULL。
- 状態はPENDING／ASSIGNED／OUTSIDEの3値のみ。初期値PENDING。
- CHECK制約で「ASSIGNEDなら担当者あり、他の状態なら担当者なし」を各方向に保証する。
- groupsとusersの参照は外部キー制約で保護。usersにUNIQUE(id, group_id)を追加し、matchesの担当者とgroup_idから複合外部キーを張る。これによりDBでも別グループの担当者を防げる。全接続でforeign_keysを有効化する。
- 退会・グループ削除の更新処理は16章を参照。
- going_version／returning_versionは同時操作対策の番号。初期値0、更新ごとに1加算。古い画面からの取り下げで、新しく決まった担当まで消えることを防ぐ。この2列を使用する。
- distance_kmの入力範囲は確定仕様書3-3を参照。入力検証にはDecimalを使い、有限の十進数のみ受け付ける。表示・集計は小数第1位にそろえる。
- 履歴専用テーブルは作らず、現在のmatchesから算出。曜日も保存せず日付から計算。
- SQLiteファイルはv2フォルダ内のinstance/sougeishare_v2.db。

## 7. 主な処理の流れ

### グループ作成・参加

新規グループと最初のユーザーは同じトランザクション（一まとまりの保存）で扱う。ユーザー登録失敗時に空グループだけ残さない。ID重複はDBのUNIQUEでも確認する。参加コード不明の場合は登録しない。成功時はセッションを作り直し、新しいCSRFトークンを用意する。

### ログイン

IDでusersを検索 → 保存済みハッシュと入力パスワードを照合 → 成功時に内部ユーザーIDをセッションへ保存 → 一覧へ。毎リクエストでユーザーと所属をDBから確認し、フォームのgroup_idを信頼しない。失敗案内は「ユーザーIDまたはパスワードが違います。」にそろえる。

### 担当更新と競合対策

図：[担当更新シーケンス](diagrams/06.png)

UPDATEのWHEREにはid、ログイン中のgroup_id、その方向の現在状態とversionを含める。担当する／グループ外はPENDINGのときだけ。本人以外の取り下げは許可するが、古い画面の更新番号なら拒否。成功した場合だけ完了案内する。別グループの試合の存在や担当名は返さない。

### 登録・削除・集計

試合登録：所属確認 → 入力検証 → group_id付きINSERT → 一覧へ。
削除：確認画面のOK → CSRF・所属確認 → idとgroup_idを条件にDELETE → 一覧へ。削除対象が既にない場合も正しく案内する。

SQL集計方針：行き担当と帰り担当をUNION ALLでまとめて、同グループのusersにLEFT JOINする。担当0回の人も表示。回数・距離の計算ルールは確定仕様書3-4を参照し、COUNT・SUMで実装する。グラフの幅＝本人の総距離÷グループ最大総距離×100。全員0kmなら幅0にして0km表示。人数に上限を設けず縦方向に増やす。

## 13. 公開利用と簡潔さの方針

- ローカル学習だけでなく実際に公開して使ってもらう前提。公開先・公開手順は別途確認する。
- app.pyとdatabase.pyを中心にし、複雑なクラス構成や不要なライブラリを追加しない。関数・変数をわかりやすく命名し、説明コメントはコードの上に置く。
- パスワードのハッシュ化、所属確認、CSRF、同時操作時の上書き防止は維持する。
- 公開時のHTTPS、開発用サーバーとdebugの扱い、秘密値・DBの保持、実装済みの試行制限と公開先の接続元IP設定は公開設計時に確認する。現段階では公開済み・公開の安全性確認済みとはしない。

## 14. 実装時の共通処理

- 連続試行の抑制用にauth_attemptsテーブルを追加する。業務用のgroups／users／matchesとは独立し、IPアドレス等はSHA-256でキー化して保存する（匿名化の保証ではない）。期限切れ行は削除する。
- 10分間のPOST上限：ログインは接続元60回・ユーザーID単位20回、参加は接続元20回、グループ作成は接続元10回。超過時は429と日本語案内。ログイン・参加・作成の共通関数にまとめる。正常な送信も数えるため、家庭や学校で同じ接続元を共有する場合は上限に注意。
- request.remote_addrを使用。公開先のプロキシ設定は別途確認し、無条件に転送ヘッダーを信用しない。
- app.pyはcreate_app関数で構成し、通常実行と一時DBでのテストを分ける。起動時にCREATE TABLE IF NOT EXISTSを実行する。既存DBへの列追加は16章を参照し、既存データを削除しない。
- セッション有効期間は12時間。HTTPS公開モードではSecure Cookieを有効にし、秘密値は環境変数で必須設定。ローカル実行は127.0.0.1、debug無効。
- CSRFトークンはsecrets.token_hexで半角文字を生成。送信値の形式をチェックしてからcompare_digestで比較する。全POSTを共通で検証。
- 名前・会場は前後空白を除去して長さを確認。距離は通常の十進表記のみ（例10、10.5）で、指数表記や小数第2位は拒否。試合日はYYYY-MM-DDで検証。
- 正しいCSRFでも、未ログイン操作はログインへ移動。別グループIDへの更新は存在を知らせず拒否。

## 16. 退会・グループ削除とDB互換処理

図：[退会処理](diagrams/10.png)、[グループ削除処理](diagrams/11.png)

- users.is_active：INTEGER NOT NULL DEFAULT 1、0か1のみ。1=利用中、0=退会済み。セッションの本人取得・ログイン照合で利用中を確認。履歴は退会済みも取得する。
- database.init_dbでPRAGMA table_infoを確認し、列がない既存v2にだけALTER TABLEを実施。BEGIN IMMEDIATEで列追加を直列化。既存行は1で保持。DB削除やseed投入はしない。
- 本人のパスワードと確認チェックを検証してから退会。日本時間の当日を標準datetime・UTC+9で計算。matches.match_date >= 当日の本人担当だけ解除し、方向別versionも1加算。同じトランザクションでis_active=0。
- group_deleteはフォームのgroup_idを使わず、ログイン本人の所属のみ対象とする。BEGIN IMMEDIATE後に本人が利用中であること、パスワード、保存済みコードを確認。成功時はmatches→users→groupsを一括削除。
- 退会・削除は10分間10回の試行制限。CSRFとパスワード検証を共通化。全メンバーのセッションは次のリクエストでDB照合時に無効化。
- 退会と同時に試合操作が来ても、INSERT/UPDATE/DELETEの条件で操作本人が利用中か再確認する。担当解除の更新番号変更も古い画面を保護。
- 最後の利用中メンバーの退会画面には注意を表示。グループ自動削除はしない。復帰・同一ID再登録・コード再発行は追加しない。
